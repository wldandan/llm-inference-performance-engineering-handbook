## 图1-1 一次流式请求的两个视角

### 对应正文

1.0 一次请求有两个视角

### 核心问题

客户端看到的请求、chunk 和结束信号，为什么不能直接等同于服务端的内部阶段？

### 核心观点

- 上方只画客户端可以记录的事件。
- 下方只画服务内部的粗粒度过程。
- 两条时间线通过请求和流式返回相连，但不画成逐节点一一映射。

### 不应出现的内容

- Gateway、Scheduler、Worker 等组件拓扑。
- Prefill、Decode、Sampling 或 KV Cache 的内部机制。
- TTFT、ITL 的正式定义和性能结论。

### 阅读路径

先从上方“客户端观察”由左向右阅读，再看下方“服务内部”的粗粒度过程，最后看跨泳道的请求与流式返回关系。

### Wireframe

~~~text
客户端观察  [发出请求] ----------------> [首个 chunk] -> [后续 chunks] -> [流结束]
                 |                              ^              ^
                 v                              |              |
服务内部      [接收] -> [等待] -> [模型执行] ----+--------------+-> [结束处理]
                                      持续流式返回
~~~

### 图中文字

- 客户端观察
- 发出请求
- 首个 chunk
- 后续 chunks
- 流结束
- 服务内部
- 接收
- 等待
- 模型执行
- 结束处理
- 持续流式返回

### 关键结论

客户端看到的是 chunk 事件，不是服务端内部阶段的一一映射。

## 图1-2 启动服务并完成第一次调用

### 对应正文

1.2 启动并确认服务就绪、1.3 发出第一次流式请求

### 核心问题

第一次实验怎样形成一个最小、可复核的运行闭环？

### 核心观点

- 先启动服务并等待模型加载。
- 使用 /v1/models 确认 API 就绪。
- 再从第二个终端发送单请求、单并发的流式调用。
- 最终看到多个内容 chunks 和结束信号。

### 不应出现的内容

- 完整部署架构。
- 并发压测、参数矩阵或性能排名。
- 服务端内部状态和调度细节。

### 阅读路径

从左到右完成“启动—确认—请求—观察”四个动作。

### Wireframe

~~~text
[Terminal A 启动服务] -> [/v1/models 确认就绪] -> [Terminal B 发出请求] -> [chunks + done]
       模型加载中                 API ready             1 request / 1 concurrency
~~~

### 图中文字

- START · 01
- Terminal A
- 启动服务
- 模型加载
- READY · 02
- /v1/models
- API ready
- CALL · 03
- Terminal B
- 单请求 · 单并发
- OBSERVE · 04
- first chunk
- more chunks
- done

### 关键结论

进程启动不等于服务就绪，第一次调用必须经过独立的 ready 检查。

## 图1-3 Demo 字段映射到客户端观察点

### 对应正文

1.4 读懂客户端报告

### 核心问题

报告中的字段由哪些客户端事件计算，哪些值来自服务端 usage？

### 核心观点

- ttft_ms 由请求开始与首个非空内容 chunk 闭合。
- itl_* 来自相邻非空内容 chunks 的到达间隔。
- total_latency_ms 由请求开始与流结束闭合。
- prompt_tokens、output_tokens 来自 usage；stream_chunks 来自客户端计数。

### 不应出现的内容

- Queue、Prefill、Decode 等服务端阶段。
- 指标优劣阈值或 Benchmark 结论。
- 把 chunk 数写成 token 数。

### 阅读路径

先看上方客户端时间线，再看三条时间区间，最后看右侧“计数来源”。

### Wireframe

~~~text
t0                  t1                t2 ... tn               tend
[request start] -> [first content] -> [content chunks] -----> [done]
|------ ttft_ms -----|
                     |-- itl --|-- itl --|
|---------------- total_latency_ms --------------------------|

计数来源：[stream_chunks = 客户端] [prompt/output tokens = usage]
~~~

### 图中文字

- CLIENT TIMELINE
- request start
- first content chunk
- more content chunks
- stream done
- ttft_ms
- itl_*
- total_latency_ms
- stream_chunks
- usage
- 客户端计数
- 服务端返回

### 关键结论

这些字段描述客户端观察，不足以单独证明服务端根因。

## 图1-4 第 1 章只负责跑通与观察

### 对应正文

1.5 先记住名字，不在这里解释机制

### 核心问题

第 1 章做到哪里，后续章节分别接手什么问题？

### 核心观点

- 第 1 章完成启动、调用、观察和保存报告。
- 第 2 章解释生命周期。
- 第 3 章解释组件架构。

### 不应出现的内容

- 具体优化技术。
- 章节之外的新概念。
- 把后续章节画成当前章已经掌握的内容。

### 阅读路径

从左侧第 1 章输入，经中间“Run + Observe”核心卡片，向右展开后续问题。

### Wireframe

~~~text
[启动服务] ─┐
            ├─> [CHAPTER 1 · RUN + OBSERVE] ─> [Ch2 生命周期]
[流式调用] ─┘          输出：第一次报告       ├> [Ch3 组件架构]
                                               ├> [Ch4 模型机制]
                                               ├> [Ch6 性能指标]
                                               └> [Ch8 Benchmark]
~~~

### 图中文字

- Chapter 1
