第1章 LLM 推理流程

从一次请求的生命周期出发，建立 prefill、decode、GPU、KV Cache 与性能指标之间的完整认知。

为什么第一章先讲流程

优化动作必须落到阶段

FlashAttention、KV 量化、batching、speculative decoding 解决的问题不同，不能用同一套直觉判断。

指标必须回到用户体验

TTFT 决定首响，ITL 决定流式输出是否顺滑，TPS 决定系统吞吐，但三者可能互相拉扯。

Profiling 需要地图

没有生命周期视角时，timeline 上的 kernel、空洞和同步等待很难解释。

工程问题常跨层出现

一次慢请求可能同时包含排队、prefill、KV Cache、decode、采样和网络返回的影响。

课程路线3 / 18

一次请求的全链路

1. 输入

文本、参数、上下文、停止条件进入服务。

2. 排队调度

调度器决定何时进入 prefill 或 decode batch。

3. Prefill

处理完整 prompt，写入 KV Cache，产出首 token logits。

4. Decode

逐 token 读取和追加 KV Cache，循环生成。

5. 返回

采样、detokenize、流式发送，直到结束。

生命周期总览4 / 18

Transformer 推理最小回顾

模型前向

  • token id 进入 embedding
  • 多层 attention + MLP
  • lm head 输出 logits
  • 采样器选出下一个 token

关键事实

  • decoder-only LLM 是自回归生成
  • 通常一轮只预测下一个 token
  • 输出越长，decode 循环越多
  • 历史上下文通过 KV Cache 复用
Transformer 回顾：10 分钟5 / 18

Token 生成循环

prompt tokens
  -> prefill
  -> logits
  -> sample token_1
  -> decode token_1
  -> sample token_2
  -> decode token_2
  -> ...
  -> EOS / max_tokens

讲课重点

模型不是一次性生成完整答案，而是重复执行“根据历史预测下一个 token”。这解释了为什么输出长度直接影响总响应时间。

流式输出体验本质上就是 decode 循环是否稳定。

自回归生成6 / 18

Prefill：第一个 token 前发生什么

输入

  • 完整 prompt tokens
  • position ids / attention mask
  • 推理参数与 batch 位置

输出

  • 首 token 的 logits
  • 每层 prompt 对应的 KV Cache
  • 后续 decode 的上下文状态
结论：TTFT 变差时，第一反应是看排队和 prefill；长 prompt 通常会显著拉高首响。
Prefill：13 分钟7 / 18

Prefill 常见是 Compute Bound

计算形态

完整序列进入多层 attention 和 MLP，GEMM 与 attention kernel 工作量大。

观察信号

SM / Tensor Core 利用率高，kernel timeline 中大块计算占主导。

优化方向

FlashAttention、FlashInfer、算子融合、Tensor Core 利用、减少无效 prompt。

Prefill 瓶颈8 / 18

Decode：每个 token 都是一轮循环

每轮输入

  • 上一轮生成 token
  • 历史 KV Cache
  • 当前 batch 调度结果
  • 采样参数

每轮输出

  • 下一个 token logits
  • 新 token 的 K/V
  • 流式返回给用户的文本片段
结论：输出越长，decode 轮数越多；ITL 决定流式输出是否顺滑。
Decode：12 分钟9 / 18

Decode 常见是 Memory Bound

访问模式

每步新增 token 很少，但需要读取每层历史 token 的 K/V。

观察信号

HBM 带宽高，SM 未必打满；上下文越长，ITL 越容易变差。

优化方向

KV Cache 量化、PagedAttention、cache layout、continuous batching。

Decode 瓶颈10 / 18

Prefill 与 Decode 对比

Prefill

  • 处理完整 prompt
  • 写入 prompt 的 KV Cache
  • 强影响 TTFT
  • 更容易 compute bound
  • 长 prompt 影响明显

Decode

  • 逐 token 循环
  • 读取并追加 KV Cache
  • 强影响 ITL 和总耗时
  • 更容易 memory bound
  • 长输出和长上下文影响明显
阶段对照11 / 18

GPU 生命周期视角

Timeline 上会看到

  • prefill 大块 attention / GEMM kernel
  • KV Cache 写入
  • decode 小步重复 kernel
  • 采样、同步、等待和空洞

不要只看平均利用率

平均 GPU utilization 可能掩盖排队、短 kernel、同步等待和 batch 不稳定。后续 profiling 章节会把这些现象放到 timeline 中观察。

GPU 执行过程：5 分钟12 / 18

KV Cache 生命周期

分配

请求进入后分配 cache block。

写入

prefill 写入 prompt 对应 K/V。

读取

decode 每步读取历史 K/V。

追加

每个新 token 继续写入 K/V。

释放/复用

请求结束后释放，或作为 prefix cache 复用。

KV Cache：5 分钟13 / 18

显存增长规律14 / 18

Compute Bound vs Memory Bound

类型常见阶段信号可能动作
Compute BoundPrefillSM / Tensor Core 高，GEMM 或 attention kernel 占主导FlashAttention、算子融合、Tensor Core、减少 prompt
Memory BoundDecodeHBM 带宽高，上下文越长 ITL 越差KV 量化、PagedAttention、cache layout
Scheduling Bound服务调度GPU timeline 有空洞，请求排队明显continuous batching、chunked prefill、并发策略
Capacity Bound长上下文/高并发显存限制 batch 或请求失败分页、量化、限制长度、模型并行
