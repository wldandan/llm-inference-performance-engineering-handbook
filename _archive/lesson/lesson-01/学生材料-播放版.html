第一个坑

Tokens/s 很高，
用户也可能觉得慢

为什么？用户先感受到的是 TTFT：第一个 token 等多久。流式输出时再感受到 ITL：每两个 token 之间卡不卡。
一次请求的全链路

从 prompt 到最后一个 token

01
输入文本和生成参数进入服务
02
调度决定进入哪个 batch
03
Prefill处理完整 prompt
04
Decode逐 token 循环生成
05
返回采样、解码、流式发送
🔁
Transformer 推理真相

LLM 不是一次吐完答案

它通常是一轮预测一个 token，
再把这个 token 接回上下文继续预测。

prompt -> prefill -> token_1 token_1 -> decode -> token_2 token_2 -> decode -> token_3 ... 直到 EOS / max_tokens / stop words
第 1 个关键词
Prefill
把完整 prompt一次性送进模型，计算上下文状态，写入 KV Cache，并得到第一个要采样的 token 的 logits。
⏱️
Prefill 影响什么

首 token 慢，
通常先看 TTFT

TTFT = Time To First Token第一个 token 出来前，要经过排队、tokenization、prefill、采样和返回。长 prompt 往往先把 TTFT 拉高。
🧮
Prefill 的瓶颈直觉

它更像一大块计算

🔥常见 Compute Boundattention / GEMM 工作量大
📈看 SM / Tensor Core利用率高时说明 GPU 在认真算
📏Prompt 越长TTFT 越容易变差
⚙️优化方向FlashAttention、算子融合、减少无效上下文
第 2 个关键词
Decode
第一个 token 之后，模型开始逐 token 生成。每一步读取历史 KV Cache，追加新 token 的 K/V，再采样下一个 token。
💬
Decode 影响什么

输出卡不卡，
重点看 ITL

ITL = Inter-Token Latency相邻 token 的间隔决定流式输出是否顺滑。输出越长，decode 循环越多，总耗时越容易增长。
🧱
Decode 的瓶颈直觉

它更像反复读历史

📚读取 KV Cache每层都要看历史上下文
🚰常见 Memory BoundHBM 带宽容易成为限制
🧵调度很关键batch 太小吃不满，太大又可能等
🧊优化方向KV 量化、PagedAttention、Continuous Batching
核心对比

Prefill

  • 处理完整 prompt
  • 写入 prompt 的 KV Cache
  • 强影响 TTFT
  • 更容易 compute bound

Decode

  • 逐 token 循环
  • 读取并追加 KV Cache
  • 强影响 ITL
  • 更容易 memory bound
KV Cache 生命周期

它是 prefill 和 decode 之间的桥

01
分配请求进入后拿 cache block
02
写入prefill 写入 prompt K/V
03
读取decode 每步读取历史 K/V
04
追加新 token 继续写入 K/V
05
释放结束后释放或复用
💾
显存直觉

上下文越长，
KV Cache 越大

KV Cache 显存 ≈ 层数 × token 数 × KV hidden 维度 × 2(K 和 V) × dtype bytes

影响最大的一般是：上下文长度、并发、dtype、KV heads。

🧭
瓶颈判断

慢了以后，先别急着开优化

🧮Compute BoundSM / Tensor Core 高，prefill 常见
🚰Memory BoundHBM 带宽高，decode 常见
🚦Scheduling Boundtimeline 有空洞，请求在等
📦Capacity Bound显存限制 batch 或上下文
