# 课堂讨论卡：从现象到证据

> 来源：提取自 `_archive/lesson/lesson-01` 的课堂提问、常见误区和 Demo 观察任务。

## 开场问题

1. 一个服务的平均 Tokens/s 很高，是否一定代表用户体验好？
2. 用户说“第一次响应慢”和“输出过程卡顿”，分别应该先看什么？
3. GPU 利用率很高，是否就说明系统已经优化得很好？

## 观察任务

让学员先观察客户端或服务报告，再回答：

- 请求是否成功进入服务？
- 首个内容何时到达？
- 后续内容是否持续返回？
- 流是否正常结束？
- 当前数据是客户端观察值、服务阶段指标，还是 GPU 资源指标？

## 追问路径

```text
现象 → 影响哪个 Outcome → 位于哪个 Stage → 消耗哪类 Resource → 需要什么 Evidence
```

例如：

| 现象 | 不要直接下的结论 | 下一步问题 |
|---|---|---|
| 首 token 慢 | 一定是 Prefill 慢 | Queue、Tokenization、Prefill、网络分别占多少？ |
| GPU 利用率低 | GPU 性能不足 | 请求是否在排队、等待外部依赖或被调度间隙打断？ |
| TPS 提升 | 优化一定成功 | TTFT、P95、Goodput、质量和成本是否变差？ |
| 上下文变长后变慢 | 一定是模型算力不够 | Prompt、KV Cache、显存带宽和缓存命中发生了什么？ |

## 课堂收束

- Prefill 主要影响首响，Decode 主要影响输出节奏；这是一种分析起点，不是根因结论。
- GPU Utilization 是资源信号，不是业务结果。
- 任何优化都要在相同 Workload 下与 Baseline 对比，并记录收益成立的条件。
- 没有证据时使用“候选假设”或 `needs_evidence`，不要把最长阶段直接写成 Root Cause。
