# LLM 推理实验规范与指标体系 v1.0

> 目的：让书中、Demo 和 Workshop 的性能数字可复现、可比较、可解释。
> 原则：指标名称不如测量点和公式重要；报告必须同时保存名称、测量点和公式版本。

## 1. 实验分级

|级别|环境|用途|允许得出的结论|
|---|---|---|---|
|L1|CPU / 无 GPU|验证公式、状态机、schema、报告和分析逻辑|“机制/计算正确”，不得声称真实推理性能|
|L2|单机单 GPU|Core 优化实验|对指定模型/硬件/版本/workload 的因果结论|
|L3|多 GPU / 多机|并行、路由、PD、MoE、扩缩容|对指定拓扑与部署的系统结论|

每个实验必须声明级别。Advanced 实验若无法提供 L3 环境，可以附 L1 trace replay / case study，但必须标记为降级版本。

## 2. 一次标准实验的生命周期

### 2.1 Preflight

运行前必须：

- 校验 manifest 必填字段和 schema 版本；
- 记录 Git commit、容器 digest、Python/driver/CUDA/框架/模型 revision；
- 校验模型、tokenizer、dtype、量化方法、最大上下文和并行配置；
- 校验 GPU 型号、数量、显存、拓扑、MIG、功耗/时钟策略；
- 探测引擎 capability，确认 baseline/optimized 参数确实生效；
- 等待服务 ready，并发送 correctness smoke request；
- 计算 workload 文件哈希，禁止 A/B 使用不同输入而不报错。

### 2.2 Warmup

- Warmup 请求与测量请求分开计数，不进入正式统计。
- 推荐下限：至少 20 个请求且持续不少于 30 秒；实际以 GPU 时钟、显存分配、吞吐和 TTFT 进入稳定区间为准。
- 若使用 Prefix Cache，必须明确 warmup 是否允许填充缓存；未明确则报告无效。
- 编译、CUDA Graph capture、模型 lazy initialization 均应发生在 warmup。

### 2.3 Measure

- 正式测量每个 trial 推荐不少于 100 个成功请求或 120 秒，二者先满足者不得自动停止，默认两者都满足后停止；资源受限的课堂短跑可降低，但要在报告中标注 `teaching_short_run: true`。
- 同时保存逐请求记录和聚合结果，不能只保留平均值。
- 客户端、服务端和 GPU 采样各自保留时钟来源；跨机 trace 需记录同步方式。
- 到达模型必须声明：closed-loop concurrency 或 open-loop request rate，不允许只写“并发 8”。

### 2.4 Repeat

- 每个配置至少 3 个独立 trial；正式参考结果推荐 5 个。
- A/B 顺序推荐 `A-B-B-A` 或按随机种子随机化，控制温度、频率降档和后台噪声。
- 每个 trial 都记录独立环境快照；不要把多个 trial 的请求拼成一个虚假的单次分布。
- 若目标是测冷缓存，每个 trial 重启/清空缓存；若目标是测热缓存，必须先达到指定命中率。

### 2.5 Analyze / Decide

只有同时满足以下条件才接受优化：

1. 可比性检查通过；
2. 主指标达到预注册阈值或置信区间不跨越“无收益区”；
3. guardrail 指标未越界；
4. correctness/quality gate 通过；
5. 结论包含收益边界和反例 workload。

## 3. 实验变量控制

### 3.1 必须固定的控制变量

- 模型 ID、revision、tokenizer revision；
- 引擎与容器版本；
- dtype、量化、上下文上限、parallelism；
- GPU 型号/数量/拓扑和功耗策略；
- 请求集内容与顺序策略；
- 输入/输出 token 分布；
- sampling 参数与 seed；
- 到达模型、请求率/并发、测量窗口；
- streaming 与 endpoint；
- 缓存初始状态；
- 采样器版本和统计方法。

### 3.2 单变量原则

Baseline 与 optimized 必须声明：

- `primary_factor`：唯一有意改变的因素；
- `expected_effect`：预期影响的主指标和方向；
- `guardrails`：不得恶化的指标；
- `allowed_differences`：由该因素必然带来的派生配置差异。

发现未声明差异时，报告状态应为 `not_comparable`，而不是继续输出一个看似精确的百分比。

## 4. 工作负载规范

### 4.1 四类基础形状

|ID|输入/输出形状|主要压力|
|---|---|---|
|S-S|短输入、短输出|启动、调度、交互延迟|
|L-S|长输入、短输出|Prefill、TTFT、attention|
|S-L|短输入、长输出|Decode、KV、TPOT|
|L-L|长输入、长输出|容量、混合资源、稳定性|

每个 Workshop 至少选择一个主要形状和一个反例形状。只在单一 shape 上有效的优化不得被写成普遍结论。

### 4.2 服务工作负载附加维度

- arrival：open-loop Poisson/trace replay 或 closed-loop concurrency；
- prefix reuse：0%、低、中、高，及 cache cold/warm；
- 长短请求混合比例；
- RAG 检索候选数、上下文长度、重排器；
- Agent 步数、工具扇出、串并行结构、超时/重试；
- 租户/优先级分布；
- 请求取消和失败比例。

## 5. 核心指标定义

### 5.1 请求级时间点

设：

- `t_send`：客户端完成发送请求的单调时钟时间；
- `t_first`：客户端收到第一个非空内容 token/chunk 的时间；
- `t_last`：客户端收到最后一个内容 token/chunk 的时间；
- `N_out`：服务 usage 或可信 tokenizer 得到的输出 token 数；
- `T0`：正式测量窗口内第一个请求发出时间；
- `T1`：正式测量窗口内最后一个请求完成时间。

### 5.2 延迟

|指标|公式|说明|
|---|---|---|
|TTFT|`t_first - t_send`|包含客户端可见的网络、排队、prefill 和首 token 开销|
|E2E|`t_last - t_send`|请求端到端完成延迟|
|TPOT|`(t_last - t_first) / (N_out - 1)`|每请求计算，排除首 token，再对请求聚合|
|ITL|连续两个**流式输出事件**的间隔|按 gap 聚合；一个 chunk 含多 token 时不等于 TPOT|
|Queue delay|`server_prefill_start - server_admit`|仅可用同一服务端时钟计算|

`N_out < 2` 时 TPOT 为 null，不得填 0。空 SSE、缺 `[DONE]`、usage 不可信等必须记录 termination reason。

### 5.3 吞吐与有效吞吐

|指标|公式|说明|
|---|---|---|
|Output TPS|`Σ successful_output_tokens / (T1 - T0)`|系统级共享窗口|
|Input TPS|`Σ successful_input_tokens / (T1 - T0)`|用于 Prefill 能力|
|RPS|`successful_requests / (T1 - T0)`|系统请求吞吐|
|Goodput|`requests_meeting_all_SLO / (T1 - T0)`|同时满足 TTFT/TPOT/E2E/质量/错误约束的吞吐|
|Capacity knee|满足 SLO 时的最大稳定 request rate/concurrency|必须用扫描曲线求得|

禁止使用“各请求 `output_tokens / request_latency` 的求和”代表系统 Output TPS；这个值只能作为 legacy/debug 指标。

### 5.4 稳定性与正确性

- success rate；
- timeout / cancelled / rejected / OOM / protocol_error 比例；
- incomplete stream rate；
- 输出 token 数达到率；
- 任务质量分数或固定样本回归；
- 多次 trial 的 CV、median 和置信区间。

### 5.5 资源与成本

- GPU memory：allocated/reserved/KV used/peak；
- GPU utilization、SM occupancy、Tensor Core 利用率；
- HBM throughput、kernel launch gap、CPU utilization；
- 能耗：J/request、J/output-token；
- 成本：$/1M output tokens、$/successful request、$/good request；
- 扩展效率：`throughput_N / (N * throughput_1)`；
- 通信：collective time ratio、network bytes、KV transfer time。

资源指标必须注明采样器、采样周期和聚合方法。压测前后两个 `nvidia-smi` 快照不能表示 peak。

## 6. 统计规范

### 6.1 报告的最小统计量

- latency：count、mean、p50、p95、p99、max；
- throughput/goodput：每 trial 一个点，跨 trial 报 median、min/max、95% bootstrap CI；
- error/quality：分子、分母和比例；
- improvement：方向感知的相对变化，并同时给绝对差值。

### 6.2 稳定性门槛

以下是首批 Spike 的预注册起点，不是跨硬件的永久真理：

- steady baseline 的 Output TPS trial CV ≤ 5%；
- TTFT p95 trial CV ≤ 10%；
- 成功率 ≥ 99%，或全部失败均为实验预期的显式拒绝；
- 优化收益需超过测量噪声：相对变化至少为 baseline CV 的 2 倍，且 guardrail 不越界。

若不满足，应先标记 `unstable` 并调查环境，不进入优化结论。

## 7. SLO 与 Goodput

SLO 必须由用例定义，不能给全书设一个“万能毫秒数”。推荐预注册：

```yaml
slo:
  ttft_ms: 500
  tpot_ms: 50
  e2e_ms: 10000
  success_rate: 0.99
  quality_min: null
```

上述数字只是 manifest 语法示例，不是课程默认阈值。每个案例应解释阈值来自交互体验、业务截止时间还是容量目标。

## 8. 可比性检查

报告对比前自动检查：

- schema major version 相同；
- model/tokenizer revision 相同；
- engine/container/hardware/topology 相同；
- workload hash、token 分布、到达模型相同；
- warmup/cache policy 相同；
- measurement duration/request count 同等级；
- A/B 只有允许的配置差异；
- 不存在未解释的 throttling、OOM、重启或降频。

结果分三级：`comparable`、`comparable_with_warnings`、`not_comparable`。

## 9. 工件目录约定

```text
runs/<experiment-id>/<timestamp>/
├── manifest.resolved.yaml
├── environment.json
├── server-args.json
├── requests.jsonl
├── request-records.jsonl
├── metrics.json
├── report.json
├── report.md
├── server.log
├── gpu-timeseries.csv
└── profiles/
```

仓库只提交经过审阅的小型参考报告和必要 trace；大型原始 profile 放对象存储，并在 report 中保存 URI 与 SHA-256。

## 10. 教学报告模板

每个 Workshop 的最终报告固定回答：

1. 我们改变了什么？
2. 为什么预期它会影响主指标？
3. 环境和 workload 是否可复现？
4. 瓶颈证据是什么？
5. 主指标变化是否超过噪声？
6. 哪些 guardrail 变差了？
7. 收益在什么范围成立？
8. 什么情况下不应使用该优化？
9. 原始工件在哪里，如何重跑？

## 11. 外部口径对齐

本规范采用当前 vLLM 和 NVIDIA 文档共有的客户端测量点：TTFT 是发送请求到首个流式输出，TPOT 排除首 token，系统 TPS 使用整次 Benchmark 的共享时间窗。特别保留 ITL 与 TPOT 的区分，因为投机解码可能在一次流式输出中返回多个 token。

正式落地实现时，应在依赖升级 PR 中复核：

- vLLM Benchmark CLI: <https://docs.vllm.ai/en/latest/benchmarking/cli/>
- NVIDIA NIM LLM Metrics: <https://docs.nvidia.com/nim/benchmarking/llm/latest/metrics.html>
- NVIDIA GenAI-Perf Goodput: <https://docs.nvidia.com/deeplearning/triton-inference-server/archives/triton-inference-server-2670/user-guide/docs/perf_analyzer/genai-perf/docs/goodput.html>
