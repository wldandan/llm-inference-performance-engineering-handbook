## 图1-1 第一个 LLM 服务的最小运行链路

### 对应正文

1.1 准备运行环境

### 核心问题

一次 LLM 调用要经过哪几段，本章的实验边界画在哪里？

### 核心观点

- 只画四个环节：客户端、vLLM API、模型、GPU。
- 客户端与服务端在同一台主机上，通过 `127.0.0.1:8000` 连接。
- 环境信息（Python / vLLM / Driver / GPU / Model）作为这条链路的前提标注在旁。

### 不应出现的内容

- Gateway、Router、Scheduler、Worker 等组件划分（属于第 4 章）。
- Queue、Prefill、Decode 等内部阶段（属于第 2、3 章）。
- 任何延迟、吞吐或利用率数字。

### 阅读路径

从左到右单向阅读，四个环节一条直线。

### Wireframe

~~~text
[客户端] --HTTP--> [vLLM API] --> [模型] --> [GPU]
   同一台主机 · 127.0.0.1:8000

环境前提：Python / vLLM / Driver / GPU / Model
~~~

### 图中文字

- 客户端
- vLLM API
- 模型
- GPU
- 127.0.0.1:8000
- 同一台主机
- 环境前提
- Python / vLLM / Driver / GPU / Model

### 关键结论

先跑通本机最短链路，再考虑跨机访问和内部结构。

## 图1-2 三层就绪证据

### 对应正文

1.3 如何确认服务已经就绪

### 核心问题

“服务已启动”至少有三种含义，它们分别证明什么、不证明什么？

### 核心观点

- 三层自下而上：进程、模型列表、请求响应。
- 每层标注“能证明什么”和“仍不能证明什么”。
- 上一层通过不代表下一层通过；三层都通过才算最小闭环。

### 不应出现的内容

- 服务端内部阶段或组件。
- 失败排查步骤（1.7 用表格表达，不重复画图）。
- 性能是否达标的判断。

### 阅读路径

自下而上三层，每层右侧读“能证明 / 不能证明”。

### Wireframe

~~~text
第三层  [请求响应] 发送 Chat Completions   能证明：链路完整可用
                                          不能证明：性能稳定、容量足够
           ↑
第二层  [模型列表] 请求 /v1/models         能证明：API 可访问、模型可发现
                                          不能证明：模型能完成一次生成
           ↑
第一层  [进程]     进程持续运行            能证明：进程已创建
                                          不能证明：模型是否加载完成
~~~

### 图中文字

- 第一层 · 进程
- 第二层 · 模型列表
- 第三层 · 请求响应
- 进程持续运行
- /v1/models
- Chat Completions
- 能证明
- 不能证明

### 关键结论

进程存在只是第一层证据，三层都通过才算服务可交付。

## 图1-3 同步请求字段与响应验收项

### 对应正文

1.5 检查完整响应

### 核心问题

请求里写了哪些字段，响应回来要按什么顺序检查？

### 核心观点

- 左侧是请求的五个字段，标出必需与可选。
- 右侧是响应的五个验收项，按正文顺序编号。
- 中间用一条箭头连接，明确 `stream=false` 意味着一次性返回完整 JSON。

### 不应出现的内容

- chunk、SSE、流式事件或首包时间。
- token 数、耗时等具体数值（图中只放字段名）。
- 服务端阶段归因。

### 阅读路径

先读左侧请求字段，经中间箭头，再从上到下读右侧五个验收项。

### Wireframe

~~~text
请求 (stream=false)          一次性完整响应
┌──────────────────┐        ┌────────────────────────┐
│ model      必需  │        │ 1 model 是否为目标模型 │
│ messages   必需  │ ─────► │ 2 role = assistant     │
│ max_tokens 可选  │        │ 3 content 非空         │
│ temperature 可选 │        │ 4 finish_reason        │
│ stream=false     │        │ 5 usage（缺失则留空）  │
└──────────────────┘        └────────────────────────┘
~~~

### 图中文字

- 请求
- stream=false
- model / messages / max_tokens / temperature
- 必需 / 可选
- 一次性完整响应
- model
- role = assistant
- content 非空
- finish_reason
- usage
- 缺失则留空

### 关键结论

HTTP 200 不等于验收通过，五项要逐条检查；usage 缺失时留空，不折算。
